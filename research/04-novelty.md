# 04 — Novelty & Positioning

This document is intentionally conservative. Its purpose is to prevent Faint from making a weak novelty claim in a research area with substantial prior work.

---

## The crowded ideas

The following formulations are **not strong enough** as a research contribution on their own.

### "A model chooses the next primitive"

Already overlapped by neural primitive prediction / assembly and sequential neural painting.

### "Use the residual to choose where to draw"

LIVE and later vectorization systems already use poorly reconstructed/high-loss regions for path initialization or progressive refinement.

### "Render after every step and show the model the current canvas"

Render-in-the-Loop explicitly makes this the central closed-loop mechanism for SVG generation.

### "Learn from raster images without vector labels"

Im2Vec and Neural Primitive Assembly already demonstrate raster/self-supervised vector learning.

### "Use RL to paint with a sequence of strokes"

Learning to Paint and numerous follow-ups already occupy this space.

### "Dynamically choose mutation/search operators"

Adaptive operator selection and dynamic algorithm configuration have long histories in evolutionary optimization.

---

## Stronger framing

Faint should instead be framed as:

> **cost-aware dynamic control of an exact geometric optimizer.**

The model's action is not "draw this triangle."

It is closer to:

> "Given the current visual residual, optimization trajectory and remaining compute, which search procedure is likely to produce the best gain per unit cost?"

That procedure may specify:

- primitive family,
- spatial prior,
- scale/orientation prior,
- mutation family,
- number of initial proposals,
- hill-climb budget,
- restart budget,
- fallback/broad exploration.

The classical optimizer then executes the procedure and the exact renderer judges it.

---

## Proposed research contribution

A defensible contribution could combine four pieces:

### 1. Geometric abstraction as Dynamic Algorithm Configuration

Formulate primitive-based image approximation as a state-dependent algorithm-configuration problem rather than an end-to-end vector prediction problem.

### 2. Counterfactual optimizer supervision

At identical canvas states, execute multiple search configurations and record their exact quality/cost outcomes.

This creates dense supervision such as:

```text
state s
  action A → gain .0050, cost 64
  action B → gain .0019, cost 256
  action C → gain .0041, cost 32
```

The system learns from outcomes generated by the optimizer itself rather than manually authored vector labels.

### 3. Joint visual + optimization-trajectory state

The controller observes both:

```text
what remains visually wrong
```

and:

```text
how the optimizer has recently behaved
```

This is important because the best search strategy can depend on whether a region/operator is currently yielding improvement, not just what the image looks like.

### 4. Calibrated compute fallback

Controller uncertainty determines how broadly the classical optimizer searches.

Instead of allowing learned errors to corrupt the output:

```text
confident → narrow cheap search
uncertain → broad expensive search
very uncertain → original fallback
```

The verifier remains exact throughout.

---

## The central empirical claim

The strongest initial claim is deliberately modest and measurable:

> **A state-aware controller can achieve a better reconstruction-quality / exact-evaluation trade-off than static geometric search.**

Only after experiments should stronger claims be considered.

Examples of valid measurable outcomes:

```text
same RMSE with 40% fewer renderer evaluations
```

or

```text
better LPIPS at a fixed 50k-evaluation budget
```

or

```text
controller reaches baseline quality faster while retaining exact fallback guarantees
```

Do not choose target numbers in advance.

---

## The oracle-gap requirement

The idea only makes sense if search configurations are meaningfully state-dependent.

Define:

```text
Static* = best single fixed configuration over the benchmark
Oracle  = best action for each individual state
```

Then measure:

\[
G = U(Oracle) - U(Static^*)
\]

If `G` is small, a sophisticated controller has little to learn.

If `G` is large, then the learning problem is justified.

This test should happen before model training.

---

## Why exact verification matters

Most learned vector systems must trust a learned generator and evaluate the resulting representation afterward.

Faint instead keeps a numerical verifier inside the action loop.

This gives several useful properties:

- safe fallback,
- deterministic outcome measurement,
- counterfactual labels,
- interpretable action regret,
- controller failures do not need to become accepted primitives,
- easy ablations between learned and classical components.

We should be careful not to claim this pattern is universally novel — render-and-verify ideas exist — but its use for **algorithm-configuration control of geometric search** is central to the design.

## Positioning against neighboring systems

### vs. Primitive / Geometrize

They search with fixed/random heuristics.

Faint learns **how to configure that search online**.

### vs. LIVE

LIVE improves vector path initialization and layer-wise optimization.

Faint's controller selects **search configuration and compute allocation**, not merely path initialization.

### vs. Neural Primitive Assembly

NPA predicts primitive arrangements/parameters directly.

Faint predicts **which optimization procedure to run**, leaving continuous solution construction to a classical solver.

### vs. Learning to Paint

RL painter policies directly emit stroke actions.

Faint emits **optimizer-control actions**.

### vs. StarVector / VectorArk

These learn vector representations/code from image/text.

Faint studies **amortized search efficiency** for a classical geometric optimizer.

### vs. Render-in-the-Loop

Render-in-the-Loop closes the visual feedback loop for a generative SVG model.

Faint closes a **search-control loop** around an exact black-box optimizer.

### vs. generic DAC

DAC provides the meta-algorithmic framework.

Faint contributes a concrete visual/geometric environment with spatial residual state, exact renderer feedback, primitive operators, and large-scale counterfactual data generation.

## What would make the project genuinely stronger

### Budget conditioning

Include remaining computation explicitly in state:

```text
remaining_evaluations
remaining_ms
remaining_primitives
```

Then learn different strategies at different budgets.

### Dynamic action vocabulary

Represent actions as inputs to the model rather than a fixed classification head. This allows new primitive/search operators to be added later.

### Generalization

Train on one visual domain and test on another. If the policy learns optimization behavior rather than visual memorization, it should transfer better than a pure generator.

### Anytime behavior

Measure quality at many budget cutoffs rather than one final result.

This is especially appropriate for search-control research.

### Cost-model transfer

Separate visual gain prediction from hardware cost prediction where possible. A policy could then be re-optimized for CPU/GPU/edge environments without retraining the entire visual representation.

---

## Claims to avoid until proven

Avoid wording such as:

- "first"
- "state of the art"
- "guaranteed faster"
- "learns optimal search"
- "generalizes to any image"
- "decision models outperform RL/heuristics"

A paper-quality novelty search and experiments are needed before those claims can be made.

---

## Working one-line thesis

> **Faint amortizes geometric optimization by learning which exact search computation is worth performing next.**

That is the positioning the rest of the project should protect.
